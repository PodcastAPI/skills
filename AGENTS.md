# Agent Instructions

This is a public repository. Treat all tracked content, including skills,
plugin packages, documentation, examples, and metadata, as publicly readable.

## Public documentation

- Write for users and contributors. Focus on capabilities, installation,
  configuration, examples, supported limitations, and build instructions.
- Keep internal planning, release-readiness checklists, submission progress,
  approval history, reviewer-account setup, and incident diagnostics out of
  public files. Keep internal working notes in a private workspace outside
  this repository.
- Do not use READMEs as working notebooks. Avoid internal status sections such
  as "V1 behavior", "Submission preparation status", or "Not yet verified".
- Avoid references to the authoring conversation, such as "the supplied logo",
  "the approved name", or "we will add this in a later milestone".
- Describe implemented behavior and user-visible limitations accurately.
  Removing internal status notes must not turn planned or unverified behavior
  into a claim that a feature is available or tested.
- Keep public changelogs and required package metadata factual and useful.
  Do not include private credentials, personal account details, or internal
  publishing procedures in them.

Before finishing a documentation change, read it from a first-time user's
perspective and remove internal process notes and temporary debugging history.
